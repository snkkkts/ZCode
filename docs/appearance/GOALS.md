# ZCode 可定制外观系统：总目标与实施约定

更新日期：2026-09-22

当前阶段：第一批基础外观功能已实现；完整工作区覆盖仍待后续验收。

文档性质：本项目的目标、范围和验收依据；不是已实现功能清单。

## 1. 总目标

为 ZCode 建立可持续维护的外观系统，让用户通过设置界面定制背景图片、透明度、字体、主题颜色和细粒度文字颜色，并保存和切换自己的外观方案。

实现应便于多个 agent 分工、验证和后续接手。每次交付都必须留下与实际代码一致的变更记录，说明改了什么、实现了什么、解决了什么问题，以及验证结果和剩余工作。

## 2. 已确认的要求与当前事实

### 用户明确要求

- 支持更换背景图片。
- 支持调整透明度。
- 支持设置软件内字体。
- 支持修改主题颜色，细化到字体颜色。
- 优先采用便于 agent 维护和继续开发的工程组织方式。
- 每次更改必须有文档记录，方便其他 agent 协同。
- 第一阶段先明确总目标，再开展实现。

### 已核实的事实

- 安装包 `resources/app.asar` 中的应用版本为 `3.14.0 Preview`，采用 Electron 和 React。
- 只读检查发现界面已有颜色变量、字体变量、浅深色主题、界面与代码字号、终端字体等基础。

## 3. 功能范围

| 模块       | 目标行为                                                         | 验收要点                                             |
| ---------- | ---------------------------------------------------------------- | ---------------------------------------------------- |
| 背景图片   | 选择本地图片、清除图片；支持填充方式、位置、模糊和遮罩           | 重启后保留；图片不可用时回退；文字保持可读           |
| 区域透明度 | 背景、侧栏、主面板等区域独立调整                                 | 只调整对应背景层，不把子元素文字一起淡化             |
| 字体       | 界面、聊天正文、代码、终端分别配置字体与字号；按适用范围提供行距 | 中文回退正常；长文本不遮挡；代码和终端保持对齐       |
| 主题颜色   | 配置背景、主色、面板、输入框、边框等                             | 各主要页面一致响应；可恢复默认                       |
| 文字颜色   | 配置正文、辅助文字、链接、按钮文字及必要的状态颜色               | 悬停、选中、禁用、错误等状态仍可辨识                 |
| 代码与终端 | 接入现有高亮主题与终端配色机制                                   | 不以全局文字颜色覆盖语法高亮；主题切换后同步更新     |
| 外观方案   | 内置默认方案、自定义方案、保存、切换、导入导出                   | 校验无效配置；支持配置版本迁移；导出文件不含敏感数据 |
| 设置体验   | 实时预览、重置单项与全部恢复默认                                 | 修改可撤销或恢复；重启后配置一致                     |

背景模糊已实现；配置代码导入导出后来由用户明确要求并已实现。分区行距、软件内主题方案库等仍属待完成设计项，具体优先级按后续需求决定。

### 透明度的边界

第一阶段优先实现“软件内背景图片 + 面板半透明”。“窗口透出桌面”作为独立技术验证项，不作为第一版完成的前置条件。若用户明确要求桌面透出，再确定其优先级。

Electron 窗口透明效果需在 Windows 下验证拖动、缩放、最大化、焦点、标题栏及渲染表现；不能仅凭 CSS 预览宣称支持。

原生系统对话框、外部网页和文档自身排版不保证受应用主题完全控制。具体边界应在相关模块实现时记录。

## 4. 工程设计原则

1. 统一外观配置结构与语义化主题变量，避免在各组件散落颜色、字体和透明度配置。
2. 默认主题为基础，用户配置为覆盖层；缺失或无效字段回退到默认值。
3. 将配置定义与校验、持久化与迁移、主题应用、设置界面、特殊渲染组件适配分开组织。
4. 代码预览、差异视图、终端及独立窗口通过各自适配层接入，不能假设全局 CSS 自动覆盖所有渲染方式。
5. 图片路径与图片资产的保存、复制、导入导出策略在实现前明确；不得仅保存短期有效的临时 URL。
6. 第一版使用结构化设置，不默认开放任意 JavaScript 注入。是否提供高级自定义 CSS 留待后续评估。
7. 优先复用官方设置与主题机制，减少重复实现和未来合并上游的冲突。
8. 保持默认外观可用；异常配置应能恢复，不得导致应用无法启动。

当前模块位置与接口责任见 [DEVELOPMENT.md](DEVELOPMENT.md)，后续功能继续复用既有配置状态与主题变量。

## 5. 开发与预览方式

- 在独立源码目录开发，不直接修补当前安装包或覆盖已安装程序。
- 推荐 Fork 官方仓库，保留上游关系，并在独立功能分支上工作；仅本地开发也可先克隆官方仓库。
- 开发模式用于日常预览。界面改动通常通过热更新或页面刷新呈现；主进程、预加载脚本及运行时改动可能触发重建或需要重启开发进程。
- 是否自动重启、哪些模块需要手动重建，必须以克隆后的脚本与实际运行结果为准。
- 日常修改不要求每次重新生成安装用 `.exe`；阶段验收和发行时再执行正式打包验证。
- 开发实例使用独立数据目录，避免影响日常使用的数据；具体环境变量和启动方式按官方源码核实。

## 6. 分阶段实施

### 阶段 0：建立可维护的开发基础

- 获取正式源码并记录基线提交和版本。
- 阅读仓库规范，核实主题、设置、持久化、终端、代码预览及窗口入口。
- 合并本项目协作规范到仓库现有规范，迁移这些文档，避免覆盖上游规则。
- 跑通开发模式，记录准确启动命令、环境版本及数据隔离方式。
- 产出模块地图、实施切分和需要确认的设计问题。

完成标志：能在独立开发实例观察界面修改，有明确的源码定位和基线验证记录。

### 阶段 1：外观配置与基础体验

- 建立配置结构、默认值、校验、持久化与恢复默认能力。
- 实现背景图、背景遮罩、主要区域透明度。
- 实现界面与正文的基础字体设置、主要主题颜色和文字颜色。
- 提供设置界面与实时预览。

完成标志：上述明确范围可操作、可保存、可恢复，重启结果一致。

### 阶段 2：覆盖完整与方案管理

- 补齐代码、差异、终端、弹层和主要交互状态的适配。
- 完成方案保存、切换、导入导出与配置迁移。
- 检查中文字体、长文本、浅深色、缩放及高分屏表现。

完成标志：覆盖矩阵有实测记录；未支持区域有明确说明。

### 阶段 3：窗口效果与发行验证

- 按需求优先级评估窗口透出桌面效果。
- 验证打包后资源路径、持久化、启动及恢复默认流程。
- 形成安装、升级和回退说明。

完成标志：交付物与源码版本对应，发行验证通过；实验效果独立标记。

## 7. Agent 协作与记录约定

- 开工前阅读本文件、`AGENTS.md` 和 `CHANGELOG.md`，再读取具体模块规范。
- 每项任务声明责任范围、目标行为、依赖和验收方式；并行任务避免修改同一组文件。
- 不撤销其他 agent 或用户的改动；遇到冲突先理解并整合。
- 每次可交付变更同步更新 `CHANGELOG.md`。不要求逐次按键记录，但不得在没有记录的情况下交付或提交一批改动。
- 记录必须包含：日期、目标或问题、修改内容、涉及文件、实现结果、验证方式与结果、限制、下一步。
- 未运行的检查写明“未运行”及原因；计划、推断和已验证结果必须区分。
- 新增长期设计决策时，在本文件或独立设计文档记录原因、取舍及替代方案。
- 完成阶段或改变需求时更新本文件的阶段状态与验收范围。
- 记录引用源码相对路径和可获得的提交号；不得虚构提交号。
- 有代码改动时执行与风险相称的检查；纯文档变更仅检查内容、链接及编码，不要求构建应用。
- 保持已有文本文件的编码、BOM 和换行；新增文本使用 UTF-8。代码注释默认使用中文，仓库另有规定时遵循仓库规范。
